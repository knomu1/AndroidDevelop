# WebRTC の仕組み（解説）

このアプリで使う WebRTC が「何で」「どう動き」「どこが難しいか」をまとめた解説。実装の詳細ではなく、全体像を理解するための文書。

## 1. WebRTC とは
**ブラウザやアプリ同士が、映像・音声・データを低遅延でやり取りするための標準技術。**
Web ブラウザ（Chrome / Edge / Safari / Firefox）に最初から組み込まれており、プラグイン無しで使える。
Android 側は Google 公式の実装（libwebrtc）を組み込んで使う。

特徴:
- **低遅延**（目安 0.1〜0.3 秒）。ビデオ会議と同じ仕組み。
- **UDP** で映像を流す。取りこぼしが出ても待たずに先へ進むので、遅れが溜まらない。
- **常に暗号化**される（DTLS-SRTP が必須）。
- **相手との間の回線状況に合わせて画質を自動調整**する（解像度・ビットレート・fps）。
- 可能なら **端末同士が直接つながる（P2P）**。サーバーは映像を中継しない。

## 2. 今の方式（JPEG 送信）との違い
| | 現在（JPEG を HTTP POST） | WebRTC |
|---|---|---|
| 送るもの | 1 コマずつ独立した JPEG | H.264 などで圧縮した動画（前のコマとの差分） |
| 通信 | HTTP（TCP） | UDP（SRTP） |
| 経路 | Android → サーバー → ブラウザ | Android → ブラウザ（直接。サーバーは仲介のみ） |
| 画質調整 | 自分で実装する必要がある | 回線に応じて自動 |
| 圧縮 | CPU で毎コマ JPEG 化 | 端末の専用チップ（ハードウェアエンコーダ）で処理 |

## 3. 登場人物（全体像）
```
   Android アプリ                 シグナリングサーバー                  PC ブラウザ
 (カメラ + libwebrtc)            (C# / WebSocket など)              (Blazor + RTCPeerConnection)
        │                               │                                  │
        │ ── ① offer(SDP) ───────────► │ ── 転送 ───────────────────────► │
        │ ◄─ ② answer(SDP) ─────────── │ ◄─ 転送 ───────────────────────── │
        │ ◄─► ③ ICE candidate を相互に交換（経路の候補）◄────────────────► │
        │                                                                  │
        │ ═══════════ ④ 映像・音声（SRTP / UDP）を直接送受信 ═══════════► │
```
- ①〜③ は「**シグナリング**」。つなぐ前の打ち合わせで、ここだけサーバー経由。
- ④ が実際の映像。サーバーを通らない（同一 LAN なら Wi-Fi 内で直接）。

## 4. 構成要素
### 4.1 シグナリング（接続の打ち合わせ）
- **WebRTC は「打ち合わせの方法」を決めていない。** 自分で用意する必要がある。これが最初の「複雑さ」。
- このアプリでは、C# サーバーが WebSocket（または SignalR）で、Android とブラウザの間でメッセージを中継する。
- 交換するもの: SDP（下記）と ICE candidate（下記）。

### 4.2 SDP（Session Description Protocol）
- 「私はこういう映像を送れる／受けたい」を書いたテキスト。
- 内容: 使える**コーデック**（H.264 / VP8 / VP9 / AV1）、解像度、送信/受信の向き、暗号鍵のフィンガープリントなど。
- 送る側が **offer**、受ける側が **answer** を返し、双方が合意した設定で始まる。

### 4.3 ICE / STUN / TURN（経路の発見）
- 端末同士がどう到達できるかを探す仕組み。ルーターの内側（NAT）にいると、外からは直接つなげないため。
- **ICE candidate** ＝ つなぎ方の候補（IP アドレスとポートの組）。両者が候補を交換し、つながるものを自動で選ぶ。
- **STUN**: 外から見た自分のアドレスを教えてくれるサーバー。
- **TURN**: 直接つなげないとき、映像を中継するサーバー（最後の手段。帯域を食う）。
- **今回は同じ LAN（192.168.11.x）内なので、STUN / TURN は不要**。LAN 内のアドレス（host candidate）でそのままつながる。インターネット越しに使うときだけ必要になる。

### 4.4 暗号化（DTLS-SRTP）
- 接続時に鍵交換（DTLS）し、映像は SRTP で暗号化される。自動で行われ、設定は不要。

### 4.5 メディア（映像の中身）
- カメラ映像を**エンコーダ**で圧縮 → **RTP** パケットに分割 → UDP で送る。
- 受信側は**ジッタバッファ**で到着の揺れをならし、デコードして表示する。
- 失われたパケットは、再送要求（NACK）や、**キーフレーム（全体を送り直す）要求（PLI）** で回復する。
- **帯域推定（BWE）**: 回線の速度を測り、ビットレートを自動で上下させる。画質は落ちても、遅延は増やさない方針。

## 5. 「複雑」と言われる理由
1. **シグナリングを自作する必要がある**（上記）。メッセージの順序や、両者が同時に offer を出す衝突への対処が必要。
2. **接続の状態遷移が多い**（new → connecting → connected → disconnected → failed…）。切れた後の再接続の設計が必要。
3. **ネットワーク事情に左右される**（NAT、ファイアウォール、UDP のブロック）。
4. **ブラウザ側は JavaScript の API**（`RTCPeerConnection`）。Blazor WASM からは JS 連携（JS interop）で呼ぶ必要がある。
5. **Android 側は libwebrtc というネイティブライブラリ**を組み込む。サイズが大きく、カメラ・エンコーダとの接続（CameraCapturer 等）の設定が必要。
6. 画質のチューニング項目が多い（コーデック、ビットレート、fps、解像度の優先方針）。

→ AI に実装を任せる前提なら、**実装の難しさ自体はそれほど問題にならない**。ただし、「つながらないとき」の切り分けには仕組みの理解が役に立つ。

## 6. このアプリでの役割分担
| 役割 | 担当 | 備考 |
|---|---|---|
| 映像の送信元 | Android（libwebrtc + カメラ） | ハードウェアエンコーダで H.264 |
| シグナリング | C# サーバー（WebSocket / SignalR） | 既存の QR ペアリングを流用して接続先を伝える |
| 映像の受信・表示 | ブラウザ（`<video>` + `RTCPeerConnection`） | Blazor WASM から JS interop |
| 画質の計測 | ブラウザの `getStats()` | 解像度、fps、ビットレート、遅延、パケット損失を画面に表示 |

## 7. 画質を左右する要素（検証の観点）
- **解像度**: 720p / 1080p / 4K（端末と Wi-Fi の帯域に依存）。
- **fps**: 30 / 60。
- **ビットレート**: 高いほどきれいだが、Wi-Fi の混雑に弱い。
- **コーデック**: H.264（互換性が高い・ハードウェア対応が広い）、VP8/VP9、AV1（高圧縮だが端末の対応が限られる）。
- **劣化時の優先方針**: 解像度を守る（fps を落とす）か、fps を守る（解像度を落とす）か。
- **端末の発熱**: ハードウェアエンコードなので、JPEG 方式より低いはず（要検証）。

## 8. 想定する実装ステップ
1. **最小構成**: Android → ブラウザへ、同一 LAN で映像を表示（シグナリングは WebSocket）。
2. QR ペアリングを WebRTC のシグナリング接続に結びつける。
3. 画面に統計（解像度・fps・ビットレート・遅延）を表示。
4. 解像度・fps・ビットレート・コーデックを、画面から切り替えて比較できるようにする。
5. （任意）AI 要約など、1 コマを取り出す機能を追加（ブラウザ側で `<video>` から静止画を取り出してサーバーへ送る、など）。

## 9. 補足・注意
- 使用するライブラリ（Android の libwebrtc ビルド、C# 側のシグナリング実装）は、実装時に最新の状況を確認して選ぶ。
- 同一 LAN 内の検証が前提。インターネット越しにする場合は STUN / TURN の用意が必要。
- Windows のファイアウォールで、ブラウザの UDP 通信が止められていないか確認が必要になる場合がある。
